# 金额闸门 — 设计文件

**日期**：2026-09-10
**范围**：确保进入系统的每一笔金额都是对的；错误在写入前就被挡住，而不是事后靠对帐才发现。

---

## 为什么

对整个系统的 sequence 做过一次检查后，金额相关的风险集中在四点，全部都有实证：

| # | 问题 | 位置 | 后果 |
|---|---|---|---|
| 1 | 删发票会连同收款纪录一起删掉，且完全没有守卫 | `app/api/system/route.ts:6188` | 已收到的钱凭空消失，帐面对不起来 |
| 2 | 登记收款不检查金额是否超过应收，也不检查是否大于 0 | `route.ts:6027` | 超收、负数收款都进得来 |
| 3 | `asNumber(x, 0)` 遇到看不懂的输入会静静回传 0 | `route.ts:188` | 月租打错字变成 RM 0，该收的钱永远收不到 |
| 4 | 抄表没有上限合理性检查 | — | 多打一位数就是一张暴增的电费单 |

第 3 点特别危险，因为 18 个金额栏位里**只有 7 个是 `type="number"`**，其余 11 个是纯文字框；抄表的 CSV 汇入更是直接用逗号切栏，`1,200` 会把整列打乱。

另外还有一类「该收钱却没收」的问题，出帐当下没有任何提示：

- 在住但没设月租、同 unit 也没人付租：**1 位**
- 房间抄表不足两笔，这期电费收不到：**3 间**
- 合约已过期还在住：**8 位**
- 合约没有结束日：**6 位**

## 做完之后，实际差在哪

每一条都是「现在会静静出错、没人会发现」变成「当下就被挡住」。

| 情况 | 现在会发生什么 | 之后 |
|---|---|---|
| 删掉一张已收 RM 2,400 的发票 | 那 RM 2,400 从资料库整个消失，没有纪录。银行对帐时才发现帐上少一笔，已经查不出来源 | 拒绝，并告诉你已收多少、几笔 |
| 月租输入 `1,2OO`（字母 O） | 变成 RM 0。这位学生**每个月出帐都被跳过**，一年后才有人问「他怎么从来没收过钱」 | 当场报错，带栏位名与原值 |
| 抄表 `1240` 打成 `12400` | 多算 11,160 度 × 0.751 = **多收约 RM 8,381**，帐单直接寄出去 | 挡下，并附对照：「比上期多 11,160 度，全系统平均只有 89 度」 |
| RM 500 的收款打成 RM 5,000 | 发票标成已付清，多出的 RM 4,500 没有归属 | 挡下：「这张单只欠 RM 480，你要收 RM 4,800」 |
| 8 位学生合约已过期还住着 | 按下产生发票，帐就出去了，系统一句话都不说 | 预览上方列出来，看过再决定 |

共同的效果是把**「事后对帐才发现」变成「当下就知道」**。前者要花几小时倒推是哪一笔、哪一天、谁做的；后者是一行红字。

所有门槛都存在 `system_settings`，觉得太敏感一直被挡、或太松挡不住，**不用改程式也不用重新部署**，在设定页改数字就好。

## 不做什么

以下属于另外两份 spec，本次不碰：

- **撤销机制**（撤销 check-in、帐期退回 draft、撤销搬出、删除抄表）
- **完整稽核轨迹**（每一个动钱的动作都记下操作人）—— 本次只把「谁确认了可疑值」写进现有的 notes 栏位

## 决定

| 议题 | 决定 |
|---|---|
| 删一张已收过钱的发票 | **直接拒绝**，要先处理那笔款项 |
| 格式怪的金额（`1,200`、`RM 500`） | **先清理再验证**，清不动才报错 |
| 数字合法但可疑（超收、抄表暴增） | **挡下来**，可以打勾确认后放行 |
| 「该收钱却没收」 | 纳入本次范围，做成出帐前体检 |
| 验证逻辑放哪 | **共用闸门模组**，规则集中一处，门槛可调 |

## 架构

新增 `app/api/system/money.ts`，三个 export：

```ts
parseMoney(raw: unknown, fieldLabel: string, opts?: { allowNegative?: boolean }): number
checkSuspicious(kind: SuspicionKind, context: SuspicionContext): Suspicion | null
billingPreflight(db: Db, input: { cutoffDate: string }): Promise<PreflightReport>
```

`route.ts` 里 18 个金额栏位改走 `parseMoney`；三个情境守卫走 `checkSuspicious`；`billing-cycle-preview` 的回传多一块 `preflight`。

门槛值存在现有的 `system_settings` 表，不需要 migration，也不用改程式就能调。

### 为什么是共用模组而不是各自加检查

82 个动作里各自写 `if` 一定会漏，而且门槛散在 6,000 行里，之后要把 RM 3 改成 RM 5 得翻遍整份档案。集中一处的代价只是改 18 个呼叫点，而且都是机械式替换。

也不用「在 POST 入口统一拦截」：那得靠栏位名字猜哪个是金额，猜错就漏；而且超收、抄表跳太多、删发票这些情境规则塞不进一个通用拦截器。

## 元件

### 1 · `parseMoney` — 格式闸门

清理顺序：

1. 转成字串、去前后空白
2. 去掉千分位逗号（`1,200` → `1200`）
3. 去掉 `RM` / `rm` 前缀与货币符号
4. 再去一次空白

然后要求 `Number.isFinite` 且 `>= 0`（`allowNegative` 时略过非负检查 —— 押金退还是负数）。

失败就 throw，讯息带栏位名与原值：

```
「月租」看不懂这个金额：1,2OO
```

**关键差别：`parseMoney` 没有 fallback。** 现有的 `asNumber(x, 0)` 保留给真正的数值栏位（天数、笔数、人数），不再用于金额。

空字串的处理由呼叫端决定：必填栏位直接丢给 `parseMoney`（会报错），选填栏位先判空再决定要不要呼叫。

### 2 · `checkSuspicious` — 可疑闸门

回传 `null` 表示没问题；回传 `Suspicion` 表示要挡。

| kind | 触发条件 | 门槛 setting key | 预设 |
|---|---|---|---|
| `meter-jump` | 本期用量超过门槛 | `money-guard-meter-jump-kwh` | 500 |
| `overpay` | 收款超过未付余额，且超出幅度大于门槛 | `money-guard-overpay-pct` / `money-guard-overpay-rm` | 20 / 100 |
| `rent-outlier` | 月租超过上限，或等于 0 | `money-guard-rent-max` | 5000 |

讯息要带对照基准，不能只说「太大了」：

- `meter-jump` → 「比上期多 1,240 度，全系统平均只有 89 度」
- `overpay` → 「这张单只欠 RM 480，你要收 RM 4,800」
- `rent-outlier` → 「同房型平均 RM 620」

**放行方式**：请求带 `confirmSuspicious: true`。放行时把确认纪录附加到该笔资料现有的 `notes`（抄表、维修）或 `remark`（收款）栏位：

```
[已核对] 陈小明 於 2026-09-10 确认此读数无误（比上期多 1,240 度）
```

不新增栏位 —— 正式的稽核轨迹是另一份 spec 的事。

### 3 · 删发票守卫

`billing-invoice-delete` 在做任何删除之前加两道检查，都是直接拒绝：

1. **底下有收款纪录** → `这张发票已收 RM 2,400，共 2 笔。要删除请先处理这些款项。`
2. **帐期已 posted 或 verified** → `2026-08 已经过帐，不能删除里面的发票。`

第 2 条实务上等于「过帐后不能删」。要能删就得先把帐期退回 draft，那是撤销机制那份 spec 的范围。

现有那段「把维修费与押金差额退回下一期」的逻辑保留不动 —— 它是对的，只是之前跑在没有守卫的前提下。

**注意 move-in 发票**：`INV-MI-*` 是转正时开的，`cycle_id` 是 `null`，不属于任何帐期。守卫查资料时必须用 `LEFT JOIN billing_cycles`，否则这些发票会被滤掉并回报「找不到发票」—— 而目前 7 张 move-in 发票里有 5 张是收过钱的，正是最需要被挡住的那些。第 2 道（帐期状态）对它们不适用，只有第 1 道（收款）会生效。

### 4 · `billingPreflight` — 出帐前体检

在 `billing-cycle-preview` 的回传多一块 `preflight`，画面显示在预览结果上方。**只提示，不挡出帐** —— 出帐本来就是「预览 → 产生」两段式，多挡一层只会挡住正常作业。

检查项（每一项回传数量与前 20 笔明细）：

| 检查 | 判定 |
|---|---|
| `no-rent` | 在住租约月租 ≤ 0，且同 unit 没有任何人付租（排除整间出租） |
| `no-meter` | 房间抄表少於两笔，且该 unit 不是 `tnb-direct` |
| `expired-agreement` | 在住但 `agreement_end_date` 早於该帐期的截止日 |
| `no-end-date` | 在住但 `agreement_end_date` 是 null |

前两项与既有的 `unreadMeterRooms` 有重叠但角度不同：`unreadMeterRooms` 讲「这期收不到电费」，`no-meter` 讲「这间房从头到尾没建立过基准」。两者都保留。

### 5 · 画面

- **格式错误**：沿用现有的 `save()` 红色错误 banner，不用改。
- **可疑值**：错误 banner 下方多一个 `已核对，确实没错` 勾选框，勾了之后按原本的送出按钮重送同一个请求（多带 `confirmSuspicious: true`）。
- **体检结果**：预览画面上方一块，四项各一列，有问题的才显示，点数字展开明细。

## 资料流

```
表单送出
  → POST /api/system { action, ...values }
      → 登入与权限检查（既有）
      → parseMoney(每个金额栏位)         ← 格式不对就 throw
      → checkSuspicious(情境规则)         ← 可疑就 throw，除非带 confirmSuspicious
      → 情境守卫（删发票时的两道检查）
      → 写入资料库
  → GET /api/system?modules=…（既有）
```

出帐预览另外一条：

```
billing-cycle-preview
  → ensureBillingCycle（既有）
  → computeCycleInvoices（既有，不动）
  → billingPreflight                      ← 新增，只读不写
  → 回传 { rows, totals, unreadMeterRooms, preflight }
```

## 错误处理

- `parseMoney` 与 `checkSuspicious` 都是 throw，由 `route.ts` 既有的 try/catch 转成 400 与讯息，画面已经会显示。
- 讯息一律讲清楚**哪个栏位、什么值、为什么不行、怎么办**，不要只说「无效的金额」。
- `billingPreflight` 失败不能影响预览 —— 包在自己的 try/catch 里，出错就回传空的 report 并在 server log 记录，预览照跑。

## 验证

这个专案没有测试框架（`npm test` 其实是 `vinext build`），沿用既有做法：`.claude-scratch/` 一次性脚本 + 临时 route 打真正的函式，测完删掉。

| 项目 | 做法 | 期望 |
|---|---|---|
| `parseMoney` 逐案 | 临时 route 依序丢 `1,200`、`RM 1,200`、`1200.50`、`abc`、`""`、`-5` | 前三个过、后三个各自报出对应讯息 |
| 删发票守卫 | 对现有一张有收款的发票呼叫 delete | 被拒绝，讯息带金额与笔数 |
| 超收 | RM 500 的发票收 RM 5,000 | 挡下；带 `confirmSuspicious` 再送 → 放行，`remark` 出现确认纪录 |
| 抄表暴增 | 对某房间送一笔比上期多 2,000 度的读数 | 挡下，讯息带全系统平均 |
| 体检 | 跑 2026-09 的 preview | 以 2026-09-10 的资料，四项应为 1 / 3 / 8 / 6。`expired-agreement` 用帐期的截止日判定，不是当天，所以换帐期数字会变 |
| **回归** | 跑 2026-08 的 preview | **361 张发票、电费 RM 23,341，一分不差** |

最后一项是这份 spec 最重要的验收条件：这次改的是金额进入系统的路径，绝对不能改变既有的计价结果。
