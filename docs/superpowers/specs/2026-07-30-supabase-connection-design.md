# Connect the app to Supabase (full database-layer switch)

## Context

The app currently runs on Cloudflare Workers and reads/writes a local
Cloudflare D1 (SQLite) database through `drizzle-orm/d1`. The user has
already copied all schema and data into a Supabase Postgres project
(`jflhjgttirywhiwxzluj`) using the export built earlier this session
(`supabase/01_schema.sql`, `supabase/02_data.sql`).

This spec covers making the running app actually **read and write Supabase**
instead of D1 — not just having a copy of the data sitting there unused.

## Decision: full switch, not a trial connection

Confirmed with the user: rewrite the whole app to use Supabase now, rather
than proving connectivity first and deciding later. D1 stays in the repo
(untouched, unused) as a rollback safety net — nothing about it gets deleted.

## Why this is a real rewrite, not a config change

The app talks to the database in two ways today:

1. **Drizzle query builder** (`db.select()`, `.insert()`, `eq()`, joins) — this
   part is largely database-agnostic and needs only the underlying driver
   swapped.
2. **Raw D1 API** — `getD1().prepare(sql).bind(...).run()/.first()/.all()`,
   plus `d1.batch([...])`. Found **68 call sites** using this pattern across
   `app/api/system/route.ts`, using SQLite-specific syntax (`INSERT OR
   IGNORE`, `?` positional placeholders) that doesn't exist in Postgres.

`db/schema.ts` also declares all **40 tables** using `drizzle-orm/sqlite-core`
types (`sqliteTable`, `integer`, `real`). These need to become
`drizzle-orm/pg-core` equivalents (`pgTable`, `integer`, `doublePrecision`,
`boolean`). **9 columns** are boolean flags stored as SQLite integers — these
become real Postgres `boolean` columns, matching what the Supabase export
already created.

## Chosen approach: `postgres` driver + Supabase's pooled connection

Three approaches were considered:

| Approach | Verdict |
|---|---|
| **`postgres` npm driver + Supabase pooled connection (port 6543)** | **Chosen.** Keeps the Drizzle query-builder code working almost as-is; only the raw D1 calls and schema types need rewriting. Standard, well-supported path for Postgres from serverless/edge. |
| `postgres` driver + Cloudflare Hyperdrive | Same driver, routed through Cloudflare's connection-pooling proxy. Right choice once this app is live with real traffic, but the user confirmed it's local-only for now — no benefit today. Documented as a follow-up, config-only step for later. |
| `@supabase/supabase-js` (PostgREST over HTTPS) | Rejected. Doesn't support the raw SQL, multi-table joins, and batched writes this app relies on throughout — would mean redesigning queries, not just swapping a driver. More rewrite, more risk, no upside here. |

Supabase's **pooled** connection string (Supavisor, transaction mode, port
6543) is used rather than the direct connection (port 5432), because direct
connections are not meant for serverless/edge workloads that can open many
concurrent short-lived connections.

## Design

### 1. Secret handling

- New root file **`.dev.vars`** (Wrangler/Cloudflare Vite plugin's local-dev
  secrets file — confirmed supported by the installed `@cloudflare/vite-plugin`
  build) holding one line: `DATABASE_URL=<supabase pooled connection string>`.
- `.dev.vars` is **not** currently covered by `.gitignore` (only `.env*` is
  matched) — add it explicitly so the connection string can never be
  committed.
- The user fills in the real value themselves, copied from their own
  Supabase dashboard (Project Settings → Database → Connection string →
  "Transaction" pooler mode). The assistant never sees or handles the raw
  connection string/password.
- Accessed in code the same way the existing `DB`/`FILES` bindings are:
  `import { env } from "cloudflare:workers"` → `env.DATABASE_URL`.

### 2. `db/index.ts`

Replace the D1-specific `getD1()`/`drizzle(d1Binding, { schema })` with:
- A lazily-created `postgres(env.DATABASE_URL)` client.
- `drizzle(pgClient, { schema })` from `drizzle-orm/postgres-js`.
- Keep exporting `getDb()` with the same signature so callers don't change.
- Remove `getD1()` (or keep as a deprecated no-op only if something outside
  the audited 68 call sites still needs it — expected: nothing does once the
  rewrite is complete).

### 3. `db/schema.ts`

- Swap imports: `drizzle-orm/sqlite-core` → `drizzle-orm/pg-core`.
- `sqliteTable` → `pgTable` for all 40 tables.
- Column types: `integer` → `integer`/`bigint` as appropriate, `real` →
  `doublePrecision`, boolean-mode integer columns → `boolean`.
- Primary keys: SQLite `integer().primaryKey({ autoIncrement: true })` →
  Postgres `integer().generatedByDefaultAsIdentity()` (or `bigint`, matching
  what the Supabase schema export already created — `bigint GENERATED BY
  DEFAULT AS IDENTITY`).
- Preserve existing unique indexes and foreign keys as pg-core equivalents.

### 4. Query-site rewrite (`app/api/system/route.ts`, `db/auth.ts`)

- Every `d1.prepare(sql).bind(args).run()` / `.first()` / `.all()` becomes
  either:
  - A Drizzle query-builder call (preferred, where the query is simple), or
  - `db.execute(sql\`...${value}...\`)` using Drizzle's tagged-template SQL
    with real parameter interpolation (replacing `?` placeholders).
- `d1.batch([...])` (5 call sites) becomes a Postgres transaction:
  `await db.transaction(async (tx) => { ... })`.
- `INSERT OR IGNORE` (8 call sites) becomes `.onConflictDoNothing()` on the
  Drizzle builder, or raw `ON CONFLICT DO NOTHING` SQL where a raw statement
  is kept.
- `RETURNING` clauses need no change (Postgres supports this natively).

### 5. Migrations baseline

- `drizzle.config.ts` dialect changes from `sqlite` to `postgresql`.
- The Supabase database already has the current schema (created by the
  earlier manual SQL export, not by drizzle-kit). Rather than fighting
  drizzle-kit into re-detecting/re-creating existing tables, generate a
  fresh Postgres migration history from the rewritten `schema.ts` and record
  it as already-applied against the live Supabase database (mirroring how
  the original D1 setup was bootstrapped). Existing SQLite migrations in
  `drizzle/` are left in place untouched as historical record; they stop
  being used going forward.

### 6. Verification plan

Given this touches every feature in the app, re-verification is a first-class
part of this work, not an afterthought:

1. **Connectivity spike first.** Before rewriting all 68 call sites, install
   `postgres`, wire up the new `db/index.ts`, and run one trivial query
   against Supabase from inside `vinext dev` (the Cloudflare Workers-emulated
   runtime). This is the one real technical unknown — if the driver doesn't
   work in this runtime, stop and revisit the Hyperdrive or Supabase-JS
   approach before investing in the full rewrite.
2. Once connectivity is proven, do the schema + query rewrite.
3. `tsc --noEmit`, `eslint`, and `npm run build` must all pass.
4. Re-test every module end-to-end against the live Supabase data, the same
   way each feature was verified earlier this session: temporary test
   account, walk through the actual UI/API flow, confirm data reads/writes
   correctly, then delete the test data. Modules in scope: login/session,
   Dashboard, Hostel Information (availability, reservations, pricing,
   occupancy), Unit Information, Student Information, Parking, Maintenance,
   Finance, Announcements, Reports, User Management.

### 7. Rollback safety

- D1 database file, `wrangler.json` D1 binding, and `drizzle/` SQLite
  migrations are left in place, untouched. Nothing is deleted.
- All changes are plain file edits in git — revertible with `git revert` /
  `git checkout` if something goes wrong.

## Out of scope for this spec

- Cloudflare Hyperdrive setup (documented as a future step for when the app
  goes live with real traffic — config-only addition at that point, not a
  rewrite).
- Removing D1 from the repo entirely.
- Any UI/feature changes — this is purely a database-layer swap; behavior
  should be identical from the user's perspective.
