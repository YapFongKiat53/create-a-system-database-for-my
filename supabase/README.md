# Moving the Hostel Operations database to Supabase

Everything currently lives in a local Cloudflare D1 (SQLite) file. These files
recreate that database in Supabase (PostgreSQL) with all existing data,
including the login system (accounts, password hashes, roles/permissions).

Target project: `https://supabase.com/dashboard/project/jflhjgttirywhiwxzluj`

## Files

| File | What it does |
|---|---|
| `01_schema.sql` | Creates all 34 tables, with primary keys, unique constraints and foreign keys |
| `02_data.sql` | Inserts 4,183 existing rows, then re-syncs the auto-increment sequences |
| `csv/*.csv` | The same data as one CSV per table (alternative to `02_data.sql`) |

## How to import (recommended — 2 minutes)

1. Open your project → **SQL Editor** → **New query**.
2. Paste the whole contents of `01_schema.sql`, press **Run**. It should say
   "Success. No rows returned".
3. New query again. Paste `02_data.sql`, press **Run**.
   It runs in a single transaction, so it either fully succeeds or changes nothing.
4. Check **Table Editor** — you should see all the tables with data.

`02_data.sql` is ~490 KB. If the editor struggles with that much text at once,
use the CSV route below instead.

## Alternative: import the CSVs

1. Run `01_schema.sql` first (the tables must exist).
2. **Table Editor** → pick a table → **Insert** → **Import data from CSV** →
   upload the matching file from `csv/`.
3. Import parents before children, or foreign keys will complain. Safe order:

   `hostel_properties` → `hostel_units` → `hostel_rooms` → `bed_spaces` →
   `access_cards` → `unit_owner_details` → `unit_services` →
   `student_profiles` → `accommodation_assignments` → `app_roles` → `app_users` →
   `role_permissions` → `billing_cycles` → `billing_invoices` → `billing_items` →
   `billing_payment_records` → `reservations` → `reservation_charges` →
   `reservation_payments` → `parking_lots` → `maintenance_tickets` →
   `ticket_categories` → `ticket_messages` → `meter_readings` → `schools` →
   `reminder_templates` → `stored_attachments` → `announcements`

   (The remaining tables are empty — no import needed.)

## Notes on the conversion

- **Types**: SQLite `integer` → `bigint`, `real` → `double precision`,
  `text` → `text`. Permission flags and account status booleans stored as 0/1
  became real `boolean` columns.
- **IDs**: primary keys are `GENERATED BY DEFAULT AS IDENTITY`, so the existing
  id values are preserved on import, and the sequence is bumped past them at the
  end of `02_data.sql`. New records will not collide with imported ones.
- **Timestamps**: `created_at` / `updated_at` stay `text` (matching how the app
  reads them today) and default to the current timestamp.
- **Login / auth included**: `app_users` (with the real PBKDF2 `password_hash`
  values — never plaintext), `app_roles` and `role_permissions` are all in the
  export, so the two existing accounts and their permissions carry over as-is.
- **`user_sessions` — schema only, no rows**: the table is created (so the
  login code has somewhere to write to structurally), but its 10 current rows
  are local browser-session tokens tied to this machine's cookies. They mean
  nothing once copied elsewhere and expire on their own within 7 days, so they
  were deliberately left out.
- **Skipped tables**: six unused legacy tables (`hostels`, `rooms`, `students`,
  `invoices`, `payments`, `complaints`) were left out. They are empty duplicates
  of the real tables and the app never reads them.

## Verified

These files were regenerated from the live database and run against a clean
PostgreSQL 16 instance immediately before delivery: schema applied with no
errors, data imported in one transaction, **all 34 table row counts matched
the source exactly** (including the new auth tables and password hash
lengths), no orphaned foreign keys, and inserting a new row correctly
continued the id sequence past the imported data.

## After importing — pointing the app at Supabase

Importing the data does **not** switch the app over; the code still talks to D1
through the `DB` binding in `wrangler.json`, and login sessions are still
issued against that local database. Moving the app itself to run on Supabase
is a separate, larger job: swap the Drizzle D1 driver for an edge-compatible
Postgres client, move every query in `app/api/system/route.ts` and
`app/api/auth/route.ts` over, and store the connection string as a secret.
